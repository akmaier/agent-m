# Chapter 4 — Experiences from the Early Days of AI-assisted Development

**Andreas Maier, Adarsh Bhandary Panambur, Siyuan Mei, and Moritz Zaiss**
Friedrich-Alexander-Universität Erlangen-Nürnberg (FAU)

## Abstract

This chapter examines how machine learning, especially large language models (LLMs), is used in practical software-engineering workflows. Building on project experience from seminar work, it analyzes concrete prototype development scenarios, including hardware-integrated automation, web-platform tooling, and document-analysis support. The chapter discusses what current artificial intelligence (AI) tools can reliably accelerate, where limitations remain, and why software-engineering discipline is still required when using black-box model components. It introduces a practical framing of black-box, white-box, and gray-box systems, connects this framing to agentic development loops, and summarizes major technical constraints such as compute, data, and domain knowledge. The overall message is operational: AI can substantially increase development speed and scope, but quality and responsibility still depend on explicit engineering methods.

## From Possibility to Project Reality

At this point in the book, the central question is no longer whether AI-assisted development is possible. That part is already settled. The practical question is how to use these tools so they improve outcomes rather than only increasing output speed. This chapter therefore shifts from general motivation to project-grounded engineering evidence.

The project examples in this chapter come from the early days of AI-based coding workflows. After the background from previous software-engineering and AI chapters, they are especially useful because they explain why these prototypes remained limited in scale. One reason is technical maturity. Model autonomy was still limited at implementation time. A second reason is process maturity. Software-engineering and AI practices were often applied informally, without a fully structured development and validation framework.

The order follows the chapter's conceptual sequence. It starts with a compact map of useful AI-supported tasks, then moves into concrete seminar projects, and finally derives system-design consequences for black-box and gray-box development. This progression matters because short demos often hide integration cost, while semester-scale prototypes expose where effort really goes.

## Where AI Delivers in Daily Engineering Work

Current models support a wide span of software activities, including direct task completion, code generation and refactoring, documentation drafting, translation between programming languages, behavior prediction, test support, and bug-fixing loops. The practical shift compared with earlier years is not only model quality. It is workflow integration. Modern setups can connect model output to compilers, tests, and runtime checks, which tightens the feedback cycle between generation and validation.

Even with this progress, the engineering interpretation must stay strict. Plausible output is not validated output. Teams get reliable value only when model-generated artifacts pass explicit checkpoints such as compile success, test coverage, and review acceptance. In other words, generated content should enter the pipeline as candidate material, not as an unquestioned final result.

This practical viewpoint is also well aligned with the literature that underpins the chapter. A gentle introduction to deep learning provides the machine-learning foundation needed to understand what these systems could and could not do at the time [Maier 2019]. Design-pattern work for machine-learning applications already made clear that successful systems need explicit engineering structure around the model [Washizaki 2022]. On the model side, early code-focused approaches such as InCoder and UniXcoder show that code generation had already become a dedicated research topic rather than a lucky side effect of general language modeling [Fried 2023; Guo 2022]. This chapter translates that early background into small but concrete project stories.

## Three Semester Projects That Exposed Real Tradeoffs

The following project examples come from seminar work in summer semester 2023. They are useful because they do not describe hypothetical demo systems. They describe small but real projects that had to work under time pressure, imperfect infrastructure, and changing understanding of the problem. In each case, the teams moved through recognizable software-engineering stages already introduced in Chapter 2. They began with a concrete need, discussed requirements, chose an architecture, implemented a first version, tested it, and revised it. What is missing, compared with a mature industrial process, is not activity but structure. Requirements were not yet managed with full traceability, risks were discussed in meetings rather than captured in formal artifacts, and verification was serious but still too manual for large-scale AI-assisted engineering. Nonetheless, the results are noteworthy.

### Clinic Workstation Automation with a Physical Trigger

One two-person student team addressed a very concrete clinic problem. A workstation inside the clinical environment had to remain shut down most of the time because of local operating policy, but staff still needed a practical way to start it remotely when work was required. This immediately introduced an important infrastructure constraint. Clinical networks are usually not openly reachable from the public internet. The reason is not inconvenience. Hospitals and clinics handle sensitive patient data and operate machines that can influence real treatment processes. For that reason, systems inside the clinic are often separated from outside networks so that random inbound traffic, remote attacks, and accidental access are blocked as much as possible.

At first glance, the obvious solution would be remote startup over the network. That is what Wake-on-local area network (LAN) is often used for. Wake-on-LAN is a simple mechanism in which one computer sends a specially formatted network message, often called a "magic packet," to wake another sleeping computer. In office environments this can be very convenient, because an administrator can switch on a machine without physically pressing the power button. In the clinic setting of this project, however, that standard path was not available in a usable way. The team therefore had to move from a purely software idea to a combined software-and-hardware workaround.

The implemented solution used a small single-board computer, in the class of a Raspberry Pi, placed near the target workstation. Such devices are inexpensive, physically small, and well suited for lightweight monitoring and control tasks. Instead of relying on direct inbound access from outside the clinic, the device periodically checked an external trigger and then physically actuated the workstation's power switch. This is an important design idea. Inbound access from the public internet into the clinic remained blocked. Outbound polling from the small device to a controlled external service was easier to arrange. In other words, the clinic side did not expose a public server. It simply asked from time to time whether it should perform an action.

The chosen trigger was Google Sheets. Google Sheets is an online spreadsheet service, conceptually similar to a shared Excel file in the browser. On paper, spreadsheets are meant for tabular data, calculations, and collaborative editing. In practice, they can also be useful as very lightweight coordination tools, because they are easy to edit, easy to share, and already provide a simple structured interface. In this project, writing an "on" token into a spreadsheet cell acted as a remote request. The device-side polling script interpreted that cell value as a command and then activated the physical trigger. From a software-engineering perspective, this was not elegant in the long-term product sense, but it was pragmatic. It created a shared state that both sides could understand quickly and test repeatedly.

The development path already resembled a software process even though it was still informal. The team first clarified the actual requirement, which was not "build a fancy automation system," but "start one specific machine remotely under strict network constraints." They then compared solution ideas, rejected paths that depended on unavailable network features, built a minimal architecture, and validated the result repeatedly in meetings. Testing focused on whether the trigger could be set reliably, whether the device reacted correctly, and whether the workstation actually powered on under realistic timing conditions. That is very close to the Chapter 2 cycle of specification, development, validation, and iteration. What was not yet there was the stronger process shell needed for scale, such as formal threat modeling, explicit operational safety cases, a deployment pipeline, or comprehensive automated regression tests.

LLM support contributed across many steps. The models helped formulate requirements more clearly, compare hardware options, explain how to access Google Sheets through an application programming interface (API), draft initial code, and debug integration issues. They were also useful for summarizing library documentation and for resolving small merge conflicts. At the same time, this project still belonged to the early era of AI-assisted development. Context windows were smaller, syntax reliability was weaker, and internet grounding was much less robust than in current tools. As a result, progress came from many short interaction loops rather than from one long autonomous run. That makes the example especially informative today. It shows both the real usefulness of the tools and the amount of human decomposition and verification that was still required.

### StudOn Companion: Course Discovery and Timely Alerts

A second project focused on course-discovery friction in the StudOn learning environment. StudOn is a university online learning platform that hosts course pages, documents, announcements, and registration-related information. For students, one recurring problem is not understanding the platform itself, but keeping track of when new courses appear or when registration windows open and close. Missing such a window can mean missing an entire seminar, even if the actual technical task behind the reminder system sounds modest.

The team therefore designed a companion service whose purpose was straightforward: watch the relevant StudOn pages, detect changes, and alert users when something important appeared. To build that, they had to make several technical ideas concrete. One was crawling. A crawler is an automated program that visits web pages, downloads their content, and extracts the parts that matter. Another was snapshotting. A snapshot is simply a stored copy of what the system saw at a given time. By comparing a new snapshot with an older one, the software can decide whether something relevant has changed. This comparison step is called change detection. In the project, new course entries or changed registration information were the events of interest.

The architecture was simple enough to build within one semester, but rich enough to teach real lessons. The team needed a crawler that behaved reliably, a database that stored earlier findings in structured form, a web application where users could configure what they cared about, and a notification path that would surface changes quickly. A database, in this context, is simply the component that stores structured records such as course name, page address, last seen status, and change time. Without that memory, the system could not distinguish "this course has existed for weeks" from "this course just appeared today." The user-facing value came from exactly that distinction.

Here too, the story implicitly follows the software-engineering process from Chapter 2. The team began with the user-side problem, namely missing important course information because a platform had to be checked manually. They then translated that into requirements such as periodic checking, change detection, and notification. The architecture followed from these requirements. Implementation came next, and testing meant more than just checking whether the crawler ran. It also meant asking whether repeated runs produced stable results, whether duplicate alerts were avoided, and whether the system still behaved sensibly when a page changed format. Those are typical validation questions in software engineering. What remained immature was the process packaging around them. The project did not yet have the richer operational scaffolding one would expect for a production service at scale, such as formal monitoring concepts, documented privacy review, or comprehensive automated acceptance tests.

The team used ChatGPT 3.5/4.0 variants and GitHub Copilot for planning, crawler setup, web-application implementation, API integration, and database design. That support was valuable, but it was not a substitute for decomposition. The models could propose code, outline schemas, and suggest change-detection strategies. They were far less reliable when hidden assumptions about the platform or the data model were involved. The students explicitly documented the characteristic limitations of that time, including small context windows, brittle debugging interactions, and instruction misses in Copilot-style support. From a current perspective, that historical record is useful. It shows that model quality matters, but the durable engineering value still came from a clear architecture and a clear validation strategy rather than from the generated code alone.

### Paper and Speech Analysis: Fast Guidance, Careful Verification

A third project examined text, speech, and data-analysis use cases. Here the setting was less about one deployed product and more about a family of support tasks. The team looked at how AI could help with understanding scientific papers, working with spoken material that had been transcribed into text, and generating starter code for data analysis. A transcript is simply a written version of spoken language. That may come from a lecture recording, an interview, or a presentation. Once speech has been transcribed, many tasks that seem to belong to "audio" suddenly become text-processing tasks: summarize the content, identify themes, compare passages, or extract claims.

The attraction of the tools was immediate. They could rewrite dense passages into simpler language, propose first explanations of unfamiliar concepts, sketch Python code for plotting or cleaning data, and produce a first analytical structure much faster than starting from a blank page. For a student project, this was a major productivity gain because it reduced the fear of the empty screen. The model could give the team something to react to. In data analysis especially, this matters. A first script that almost works is often more valuable than no script at all, because it reveals what still has to be clarified.

At the same time, this project made the limits of that support impossible to ignore. Hallucinated facts appeared often enough that summaries could not be accepted without checking the source. Explanations were sometimes incomplete in exactly the places where careful reading mattered most. Code snippets looked plausible but occasionally used the wrong library call or silently made assumptions about data shape that were never stated in the prompt. The software-engineering lesson is subtle but important. The model accelerated exploration, but it did not reduce the need for specification and validation. In fact, by producing plausible intermediate results so quickly, it increased the importance of systematic checking.

This again mirrors the Chapter 2 process, even if in a lightweight form. The team began by defining the intended use cases, such as summarizing papers, asking questions about transcripts, or generating starter analysis code. They then implemented and compared small workflows, examined output quality, and revised their approach based on observed failure modes. What they did not yet have was a mature evaluation framework. There was no large benchmark set, no formally defined acceptance criteria for different kinds of summaries, and no stable quality dashboard. That is precisely why the project is instructive. It shows how AI-assisted work can already follow a real development cycle while still being far from the structured form needed for larger organizations or safety-relevant use.

Today, paper-assistance performance is better than it was in 2023, especially for interactive question answering and implementation support. The core rule, however, has not changed. For deep technical use, the model is best treated as a sparring partner. It can guide reading, accelerate initial understanding, and offer candidate analysis steps. Factual claims, interpretations, and implementation details still need direct cross-checking against the original source material.

## Designing Around Opaque Models: Black, White, and Gray Boxes

The chapter's main systems concept is the black-box versus white-box distinction. A black box is a component whose inputs and outputs can be observed, while its internal reasoning is largely hidden in everyday use. A white box is the opposite. Its internal logic can be inspected directly. Most ordinary software written by a development team is white-box in that sense, because the source code, tests, and control flow are visible. Most frontier LLMs, by contrast, behave like black-box components for a software team that consumes them through an interface. One can test them, prompt them, and measure them, but one cannot step through their internal reasoning in the way one debugs ordinary code.

This distinction matters because it changes how systems must be designed. If a component is opaque, the surrounding software has to compensate. That is exactly what happened, in a small way, in the semester projects. The clinic project surrounded a fragile model-guided development process with a deliberately simple trigger path. The StudOn project relied on stored snapshots and explicit change comparison rather than trusting a model to "just notice" important differences. The paper-analysis project succeeded only when claims were checked against original material. In all three cases, the unknown part was kept inside a larger structure that could still be inspected and tested.

That combination naturally leads to gray-box architecture. A gray-box system mixes opaque and transparent parts in a controlled way. The LLM may generate a suggestion, a query, a summary, or a piece of code. The surrounding software then performs deterministic checks. A compiler either accepts the code or rejects it. A database either contains the previous snapshot or it does not. A unit test either passes or fails. A retrieval component either finds the referenced document or cannot. This pattern is extremely important for modern AI-assisted development, because it turns probabilistic generation into a process that still has explicit control points.

A practical agentic loop therefore looks less mysterious than marketing language sometimes suggests. First, the system proposes an action. Second, a concrete tool executes that action. Third, deterministic signals validate the result. Fourth, the system revises its next step based on those signals. This is still software engineering. It is just software engineering with one highly capable but imperfect probabilistic component in the middle. Seen this way, black-box, white-box, and gray-box design are not abstract labels. They are design choices about where uncertainty is allowed to live.

White-box examples from machine learning itself help anchor the intuition. A decision tree can often be inspected branch by branch. A linear regression model exposes its coefficients directly. Such models are not always better, but they are easier to inspect. The broader design lesson is therefore not "avoid black boxes at all cost." It is "surround black boxes with enough transparent structure that failures stay observable, bounded, and correctable." That lesson is fully consistent with the software process from Chapter 2, especially the emphasis on interfaces, validation, and controlled evolution.

## What Still Slows Teams Down: Compute, Data, and Domain Expertise

Several constraints remain fundamental, and they explain why early AI-assisted development was promising but still limited in scale. The first is compute. Compute is the hardware capacity needed to run or train a model, often in the form of powerful graphics processing units (GPUs). More compute usually means faster iteration, larger models, and more experiments in parallel. Less compute means longer waiting times, stricter budget choices, and fewer chances to explore alternatives. This is not a side issue. It affects whether a team can iterate several times a day or only a few times per week. Teams can rent compute through commercial services or use institutional infrastructure, and both options involve tradeoffs in cost, control, data protection, and throughput.

The second bottleneck is data. Pretrained systems reduce the need to train everything from scratch, but reliable domain behavior still depends on the quality of the material used for evaluation and adaptation. A model that works well on public benchmark tasks may still fail badly in a clinic, in a university platform workflow, or in a specialized document-analysis setting. Data here does not only mean massive training corpora. It also means representative examples for testing. If the test cases do not resemble the real environment, the team learns the wrong lessons from apparently good results.

The third bottleneck is domain expertise. This is often underestimated because modern models are so articulate. Yet none of the semester projects could have been completed by generic coding support alone. The clinic project required understanding why a secure network boundary existed and why a physical workaround might be acceptable. The StudOn project required understanding what users actually miss on a course platform and why duplicate or late notifications are annoying. The paper-analysis project required understanding when an explanation merely sounds plausible and when it is actually correct. Domain expertise is what turns generic model output into task-relevant engineering decisions.

These three bottlenecks connect directly to the software process from Chapter 2. Compute influences feasibility and planning. Data influences validation quality. Domain expertise influences requirements, architecture, and risk assessment. If any one of these is weak, the process becomes fragile even when the model itself appears strong. This is another reason why the early projects remained small. They were not only constrained by model autonomy. They were also constrained by the amount of process and domain structure available around the model.

A consistent mitigation pattern is tighter grounding through deterministic systems. Integrating model outputs with compilers, tests, retrieval stores, and runtime checks substantially reduces failure risk, but only when the software process around those integrations is explicit and enforced. In practice, this means not only having the tools, but also deciding who reviews which output, what counts as success, and how failures trigger revision.

## Tooling Velocity Is Real, but Engineering Still Sets the Guardrails

Tooling is moving quickly, from code-completion assistants to agentic coding environments and no-code orchestration platforms. That acceleration is real. Tasks that once required repeated prompt rewriting, manual file copying, and constant context repair can now often be completed in one integrated loop with direct access to the codebase, the terminal, and the test suite. The threshold for obtaining a first working result has clearly dropped.

What has not changed is the role of engineering guardrails. A first working result is not the same as a dependable system. Architecture still determines whether the system can evolve. Verification still determines whether hidden faults are detected. Maintainability still determines whether the project survives beyond the initial prototype. This distinction is easy to miss when a tool produces visible progress quickly. It is one of the central lessons of the early project examples in this chapter.

Even highly specialized domains already showed this pattern surprisingly early. Magnetic resonance imaging (MRI) sequence programming is a niche expert task with difficult technical vocabulary, physics constraints, and highly structured software interfaces. Programming an MRI scanner typically requires a degree in physics plus additional training in MRI programming. Developing a new sequence used to be work on the order of a Master's thesis, which means roughly six months of effort. In the GPT4MR project, that first implementation cycle could suddenly be reduced to minutes. The Geek Box below summarizes this case, which is still part of the same early phase discussed throughout this chapter. It is especially revealing because it shows that AI-assisted coding was already useful far beyond ordinary web scripts, but only when prompt design, domain knowledge, and careful validation worked together.

> **Geek Box: GPT4MR: early AI-assisted coding in a highly specialized domain**
>
> MRI, or Magnetic resonance imaging, forms images by combining carefully timed radiofrequency pulses with magnetic field gradients. Writing such sequences is specialized work, because small code changes affect timing, physics, and finally image quality. That is why the GPT4MR project is so revealing for this chapter: it asked whether an early general-purpose large language model could already help with a narrow expert programming task [Zaiss 2024]. The authors did not use the model for vague discussion. They asked it to generate actual sequence and reconstruction code with PyPulseq, a Python interface to the vendor-neutral Pulseq format, together with the MR-zero simulation and reconstruction pipeline [Zaiss 2024].
>
> The setup also fits the early phase of AI-assisted coding very well. GPT-3.5 and GPT-4 were tested first with ordinary prompts and then with a carefully engineered GPT4MR prompt that included instructions, PyPulseq function definitions, and examples. This mattered immediately. Native prompting often produced code that called non-existing PyPulseq functions or made conceptual mistakes. The tailored prompt improved performance considerably, and GPT-4 was clearly stronger than GPT-3.5. The paper also reports a pattern that now feels familiar in agentic workflows: once errors were pointed out, or the task was decomposed into more explicit steps, the model could often repair its own output and move toward runnable code [Zaiss 2024].
>
> For software engineering, the lesson is the same as in the semester projects. The model was useful because the task, the interfaces, and the validation criteria were made explicit. It did not replace expert review. It accelerated prototyping inside a structured loop of prompting, code generation, execution, and inspection. After a detailed step-by-step prompt, GPT4MR produced a spin-echo echo-planar imaging (EPI) implementation on the first attempt. The code already runs, even though the spin-echo timing is still not perfectly aligned with the k-space center and the reconstruction still shows the typical EPI distortion artifact.
>

In the bottom row (f–j), the language model equipped with the GPT4MR context performs significantly better, producing a runnable sequence whose reconstruction shows only the typical EPI distortion artifacts.

Across all projects in this book, including those from this early phase, a consistent pattern emerged: AI coding agents were most impactful when developers had to work *outside their comfort zone*, e.g. configuring a Raspberry Pi's GPIO pins, interfacing with the StudOn database, or building a JavaScript frontend when the team's expertise was Python backends. The underlying complexity did not disappear, but the *activation energy* dropped dramatically: teams could start from a working first draft rather than a blank page. In effect, AI agents lower barriers along three axes: between programming languages and frameworks, between software and hardware domains, and between familiar and unfamiliar system architectures. Humans naturally resist context switches; LLMs, which have no comfort zone to begin with, mitigate this resistance and expand the space of designs a team is willing to explore.

For this book, the operational conclusion is therefore simple but strict. Use AI aggressively where it accelerates understanding, drafting, implementation, and exploration. Do not confuse acceleration with assurance. The software-engineering frame remains the structure that turns fast output into trustworthy results.

## Readiness Questions Before You Ship

Before adopting an AI-assisted workflow in production, teams should ask a concrete readiness set. The first question is how machine learning is actually used in the process. Is it only helping to draft documentation and code, or is it making decisions that directly affect users? That difference matters because the second case requires much stronger validation and governance.

The next question is which risks emerge when a trained model becomes part of the product itself. Risks may come from factual errors, unstable behavior, privacy leakage, biased outputs, poor failure handling, or weak recoverability. These are not abstract concerns. Every one of them can be translated into test design, review policy, and architecture choices. If a team cannot say what failure looks like, it is not ready to ship.

Teams should also ask how data dependence is reduced or controlled. Does the system rely on prompts alone, or does it ground itself in trusted sources such as curated documents, databases, or deterministic checks? This is where the gray-box idea from the previous section becomes practical. A system that only "hopes" the model will be right is fragile. A system that checks, constrains, and logs model behavior is much easier to trust.

Another useful distinction is what belongs to machine learning broadly versus deep learning specifically. Not every prediction problem needs a frontier LLM. Sometimes a smaller and more transparent model, or even ordinary rule-based software, is the better engineering choice. This is not anti-AI. It is proper system design. The right question is not "can we use the newest model?" but "which component solves this part of the problem with acceptable cost, risk, and maintainability?"

Finally, teams should ask which LLM limits are most relevant for the actual quality goals of the project. Hallucination may matter most in one system. Latency or cost may matter most in another. Data protection may dominate in a third. These questions are not checklist theater. They are practical gates that reveal whether a pipeline is robust enough for real deployment. They also make visible whether the team has progressed from early exploratory AI-assisted development toward a software process that can scale.

Compared with short project summaries, real project execution follows a different pattern. Teams move forward through iterative decomposition, repeated debugging, and explicit synchronization between requirements and implementation artifacts. The recurring irony is useful and slightly funny at the same time: the first prompt often looks impressive, but the real effort lives in integration details such as API behavior, trigger logic, data handling, and platform constraints. This is exactly the software-engineering lesson of the chapter. AI drafts quickly, while system quality is still decided by interfaces, tests, review discipline, and long-term maintainability work.

## Exercises

These exercises put the early-experience lessons of this chapter into practice. Each problem asks you to plan, implement, or evaluate an AI-assisted development workflow under realistic constraints.

**Exercise Problem 1:** Design and document an AI-assisted prototype project with one hardware or infrastructure constraint, and justify the complete development plan from requirements to validation. Start by describing the environment constraints, then define user-triggered behavior, implementation architecture, and failure handling. Example task: specify a remote workstation control prototype that must operate behind a restricted network and provide an auditable event log. Try to have the project implemented in a single prompt.

**Exercise Problem 2:** Reproduce the limitations analysis of an older LLM workflow versus a modern integrated workflow. Define one development task, execute it under both setups, and record differences in prompt length, debugging effort, and success rate. Example task: generate and refine a small web API endpoint with an older chat-style workflow and with a compiler-connected agentic workflow.

**Exercise Problem 3:** Propose a domain-specific checklist that determines when AI-generated output may be accepted, revised, or rejected in a team workflow. Include criteria for technical quality, policy compliance, data protection, and operational risk. Example task: define acceptance gates for an educational web application that processes user notifications and external API data.
