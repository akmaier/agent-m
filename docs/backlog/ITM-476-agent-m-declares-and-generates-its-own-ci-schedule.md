# ITM-476 Agent M declares and generates its own CI schedule

**REGISTER**

## Outcome

Agent M has a declared `docs/tests/schedule.md` and CI generated from it through MOD-test-schedule's accepted
`ciConfiguration` interface. The schedule assigns fast tests to pull requests and the remaining tests to the occasions
they need, within the existing two-minute pull-request job budget. The generated configuration uses working
MOD-workflow-entries interfaces for its Definition-of-Done check and JUnit result recording.

The result-record prerequisites are MOD-result-records' accepted parseOutcomes and appendResult interfaces: actual
JUnit outcomes matched to test declarations, with immutable run records added to the test-results branch. They are
implemented before the workflow entry that uses them: parseOutcomes by ITM-750, appendResult by ITM-635; both are
consumed unchanged, not implemented a second time here. The generated workflow then uses the completed entries.

The repository-host prerequisites are its accepted openPullRequest and setPipelineSchedule interfaces. Schedule
proposals use the former; GitLab nightly scheduling uses the latter. Each is implemented in its owning module before
the schedule integration uses it: openPullRequest by ITM-606, setPipelineSchedule by ITM-749. MOD-test-schedule's
findings, ciConfiguration, proposeSchedule and applyPipelineSchedule are built by ITM-742, ITM-744 and ITM-746.
This item adopts them on Agent M's own repository and builds the workflow entries it uses.

What `.github/workflows/tests.yml` and `nightly.yml` do that the generated configuration must carry when they go:

- `tests/test_release_sprint_02_c.py` reads `AGENT_M_NIGHTLY=1`; a test that runs only on some occasions reads
  `AGENT_M_OCCASION` (MOD-test-schedule, *The command*).
- `nightly.yml`'s job `bridge-build-real` (`BRIDGE_BUILD_REAL=1` under `xvfb-run`) becomes a test of a row the schedule
  ticks for `nightly`, reading `AGENT_M_OCCASION`.
- `tests/fixtures/architecture/tests/reader.test.js` is named as a test and has no readable level, so `runTests` would end
  the row `failed` before running; it is given a level or a name that is not a test's.

## Acceptance

- Use the workflow entries the generated configuration calls, `runTests` (ITM-1215), `onTestsFinished` (ITM-1209,
  ITM-1216) and `onDoneCheck` (ITM-1210, ITM-1216), the generator of ITM-1213 and ITM-1214, and Agent M's own command
  and setup (ITM-1217).
- Agent M's `docs/tests/schedule.md` declares `minutes: 2`, its command and setup; the committed
  `.github/workflows/agent-m-tests.yml` is its generated bytes; `tests/test_ci_budget.py` checks that file.
- Use the scheduling, repository-host and report-parser interfaces of ITM-742, ITM-744, ITM-746, ITM-749 and ITM-750
  and the appendResult of ITM-635 unchanged; duplicate none of them in a workflow entry.
- Validate the declared schedule with its owner's schema and findings; generated bytes reproduce the committed CI.
- Tests prove the configured occasions, complete release-candidate coverage, prohibition of paid calls on pull
  requests, ignoring job-record-only changes, and result records from actual test reports.
- GitHub CI runs the generated configuration successfully before the increment reaches GitHub main.
- A Developer who implemented none of the behavior writes its release tests and records planted-fault counterproofs.
- Replace the transitional workflows only when the generated schedule performs their required coverage.
