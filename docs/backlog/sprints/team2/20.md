### Jobs and evidence

Each implementation job receives the original item, its accepted requirements and use cases, the
module and subsystem/system decisions, the unchanged MOD-text-tools interfaces, and chapters 9, 11,
12 and 13 in full. Before generating tests its participant reads the existing guarding declarations,
descriptions and code; every test-generation job receives chapter 13 in full. Only the selected module's
source folder and tests naming it are implementation scope. Vendored library, licence and README
changes follow ITM-342 and ARC-049. No change between jobs is selected on unverified need.

Each behavior job starts with a tests-only commit and its observed product-red CI before implementation.
The declared process and default Definition of Done govern Source, independent Release and Main
decisions, each naming the exact artifact or head checked. Every new test has its recorded relevant
planted fault, failing result and restored positive; diagnosis and proof identify the actual caller and
data-flow path. No test-count quota, per-assertion quota or new gate is added. Generation-job retry limits
are fixed before their first round; they are distinct from gate decisions, for which this selection adds
no two-rejection cap.

All code, test, fault, full, native and browser execution occurs only in controlled GitHub Ubuntu CI,
with every job at most 120 seconds. Local work is limited to original/static/metadata reading and
authorized file/Git work. No personal state, external SSH host, paid service or native remote control
is used. Release tests are authored by a participant who implemented none of the guarded behavior.

### Design principles

One Team 2 sprint record and one renderer responsibility follow One Thing at a Time. The existing shared
declarations, participant register and contracts are retained (DRY); the standard per-team sprint path
and branch follow the same convention as every team (no special first case). The selection changes no
other team's record or process. Only the two selected accepted function sets are implemented (KISS and
YAGNI); no SPEC, use-case, architecture or process change is needed for this bounded increment.
