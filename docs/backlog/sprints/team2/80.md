The reading, named (AGENTS.md §6a.6):
- `EVERY CODE FILE BELONGS TO A MODULE` lets a file whose place the platform fixes — "a CI workflow" — belong to a module
  by being "named in the parts of one module". MOD-test-schedule's Parts name `tests.yml`, "since GitHub fixes their
  place, until this module generates `agent-m-tests.yml`". So `tests.yml` belongs to MOD-test-schedule.
- `CODE OUTSIDE THE ARCHITECTURE IS MOVED INTO IT`, whose jobs only move or remove, binds a file "that belongs to no
  module", so it does not bind `tests.yml`. Its approval says the same (queue `2026-10-17d`, decision 2): such files "are
  named in a module's parts, not moved … the module owns them by naming them".
- `AN IMPLEMENTATION JOB CHANGES ONLY ITS MODULES` allows "the files outside every module that one of those modules'
  files names as taken over". So a job of MOD-test-schedule may change `tests.yml` in its place.
- The split adds no behaviour and changes no expected result. So it is a refactoring job: `A REFACTORING JOB BEGINS
  WITHOUT A FAILING TEST` (CI green on every commit) and `A REFACTORING JOB CHANGES NO EXPECTED RESULT` apply, not `AN
  IMPLEMENTATION JOB BEGINS WITH A FAILING TEST`, which binds a job "that adds or changes behaviour".

Nothing here needs a change of the SPEC, a use case or the architecture, so nothing goes to akmaier.
