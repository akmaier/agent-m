The concrete evidence path is:

- `src/review-pages/kinds.mjs` gives SPEC entries `accept: "queue"` -> `src/review-pages/flow.mjs` renders a single
  entry through `service.view` -> `src/review-pages/spec-entries.mjs` calls MOD-spec-changes `entryView` -> the page
  shows current section, proposal, difference, rationale and impact list -> the person's *Accept* click calls
  `queueService.accept` -> MOD-spec-changes `acceptEntries` writes the approval record, `SPEC.md` and
  `entscheidungen.md` in one `commitFiles` call. The failure nodes are the DOM sections and the exact committed files in
  `tests/system-uc-006-approve-spec-change.test.mjs` TST-371001.
- `flow.mjs` routes `spec-entry/id=.../edit=1` to `src/review-pages/entry-edit.mjs` -> the editor opens on the entry's
  proposal and recomputes impact -> the person's *Save* click calls MOD-spec-changes `saveEntry` -> only the entry
  proposal and rationale are committed. The failure node is the commit file set in TST-371002.
- The list route asks `queueService.groups` for tickable entries -> an entry waiting for an anchor carries a shown blob
  with no current section -> `acceptEntries` refuses it alone and names the creator, or writes entries 05 then 06 when
  both are ticked. The failure nodes are the refusal text, the SPEC bytes and the order of decision rows in TST-371003.
- A stale proposal after the page was shown changes the host head before *Accept* -> `acceptEntries` compares the shown
  proposal blob to the current queue file -> no commit is made and the page names the stale proposal. The failure node is
  the absence of a write and the refusal text in TST-371004.
- Without a token on the instance route, `flow.mjs` calls `offerRecord` and MOD-approvals `fallbackAcceptLink`, so the
  page offers GitHub's new-file page for the record and the edit page offers GitHub pages for the entry files without a
  dashboard write. The instance workflow path then runs `src/workflow-entries/main.mjs` `runEntry("onApprovalsCommitted")`
  in a temporary git checkout -> MOD-workflow-entries calls MOD-spec-changes `applyApproved` -> the workflow commits only
  `SPEC.md` and the queue decisions, or fails stale with no write. The failure nodes are the fallback links and the git
  diff in TST-371005 and TST-371006.
- `tests/release-uc-006-approve-spec-change.test.mjs` reads UC-006's `realises` list and the current SPEC check lines,
  then requires every executable requirement to have evidence and every review-only requirement to be listed.

The only ambiguous reading found is UC-006's no-token split: alternative 4b names GitHub's page without a token, while
4c says that for a product a token is required because no product carries the workflow. The tests follow UC-006 by
covering the no-token GitHub fallback on the instance route and using a product token for the product acceptance path.

Counter-proof notes for the pull request/final report:

- A fault that writes the SPEC before the Accept click is caught by TST-371001 and TST-371002, which assert no write
  before the click.
- A fault that ignores the shown proposal blob is caught by TST-371004, which changes the proposal after render and
  expects no commit.
- A fault that applies queue entries in tick order rather than queue order is caught by TST-371003, which inspects the
  resulting SPEC bytes and decision-row order.
- A fault that lets the instance workflow apply a stale approval is caught by TST-371006, which runs the workflow on a
  temporary repository and expects the origin head to stay unchanged.
