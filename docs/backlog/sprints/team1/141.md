### The brief — the team agreements, stated here

Reading and reporting
- Before you start, read AGENTS.md, SPEC.md and book chapters 9, 11, 12 and 13 in full, and the use case and module files
  of your item.

  them. The Scrum Master checks that line.

  module's Uses and the callee's interface give. Import nothing the Uses leave out.
- Read each search to its last line for every count and expectation the change touches. Confirm a negative against a
  case that has to match.

Scope
- Change only the item's modules and the tests its Acceptance names. For anything else, stop and ask the Product Owner
  first.
- Before an item is selected, its planning checks the Uses of every module whose code it calls, and every test file
  outside its modules that its probe moves. An item that needs either changed goes to akmaier at planning.

  in the pull request. Or stop under AGENTS.md §6a.6 and name the sentence that is missing. Nobody changes the SPEC this
  sprint.
- If what a view derives changes, check every page that draws the changed field, with each value it can take.
- A new member of a list or family takes the form of its siblings. Before a rename, search `docs/` and `src/` for all
  readers.
- No module awaits at its top level. Run the tests of the modules that import the one you change. CI uses Node 22.
- A page you change reads nothing it does not show (`EVERY PAGE LOADS IN UNDER THREE SECONDS`).

Tests

  each file 60 seconds at most, and reports what it found.
- The probe also runs the tests of the modules whose generated files the change feeds. It renders every changed route in
  each context the dashboard gives it.
- If a probe finds a real break outside the item's modules, it reports it at once, before it runs the remaining files.

  Every changed expectation is in that commit. No counter-proof is weakened afterwards. Run
  `tests/test-document-one-line.test.mjs` before you push it.

  test's change and its `todo` go in one commit by another participant, after the code.
