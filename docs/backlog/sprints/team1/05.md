## Retrospective

**What went well.**
- Every item began with failing tests, and every new test has a recorded counter-proof.
- The gate caught the change between jobs #115 making a module's own read a requirement instead of a permission.
- The developers built to the accepted text and named each gap instead of working around it.

**What did not.**
- The sprint spent most of its time on six drafted changes to the architecture, each with up to three review rounds,
  while items waited. akmaier, verbatim: "You are sending reviews back and forth again. This is not scrum".
- Several changes designed what no item needs — how CI and the Bridge read a declared model version, release test reports
  waiting for acceptance, a rule named per path pattern. akmaier, verbatim: "Are you also following YAGNI and KISS
  principle? It seems you are adding features that nobody requested."
- The Scrum Master sent a procedure question — how an instance file follows a changed format — to a drafter as a review
  finding instead of deciding it.
- The Scrum Master pointed a developer to a test file that does not exist, and landed a draft from inside the Product
  Owner's clone.

**Changes, each with where it goes.** An agent's changes are proposals only
(`AN AGENT'S RETROSPECTIVE CHANGES NO PROCESS BY ITSELF`).
- Applied by akmaier: `SOFTWARE_MAINTENANCE.md` §0 Nr. 13 — YAGNI and KISS are mandatory, and the Scrum Master drives
  the sprint to a quick finish.
- Applied by the Scrum Master to its own working agreement with the developers: an item builds only what it names; a gap
  is noted in the pull request and the work goes on.
- Proposed, `docs/process.md` (Boundary): a gap found during a sprint is noted and collected, and drafted as one change
  only when an item needs it — instead of "drafts the change at once".
- Proposed, team agreement: a drafted change to the architecture gets one review; a finding about something no item
  builds is answered "not needed now"; a procedure question is decided by the Scrum Master.
