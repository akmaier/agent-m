Why:

- Checked on `1abd068`:

    committed by akmaier names its current blob.
  - Every requirement the items realise stands in SPEC.md, and no SPEC queue is open.
  - Each item names its modules and asks only for their folders and the tests that name them. ITM-212 to ITM-222 each
    change a module of their own, so their scopes are disjoint; ITM-223 changes tests only and starts after ITM-222.

    left out of ITM-212.

    builds MOD-identifiers.
- The goal is the part of UC-002 whose items hold or need a small correction: MOD-product-process and the modules it
  uses read the declaration, check it and turn it into the workflow. The page (ITM-220 to ITM-222) and the system and

Corrections:

- ITM-212: `historyMarks` and `lineDiff`, with `HistoryMark` and `DiffLine`, are part of it, tested as the module's file
  states them. `sha256` is not part of it.
- ITM-213: its tests also state:
  - the values that depend on other values (`requiredWhen`, `forbiddenWhen`, `variants`) in a table's row, since
    MOD-participant-list's register requires a model for every type but `person`;
  - `loadSchema` reading a schema data file in the form the owners keep theirs, `*.schema.md` (MOD-model-catalogue,
    MOD-participant-list, MOD-source-register, MOD-product-process). No module file says how such a file holds its JSON
    object. ITM-213's tests settle it, and ITM-215 to ITM-218 write theirs that way, so none of them changes
    MOD-documents.
- ITM-214: what a requirement constrains follows from the SPEC it stands in; `Requirement` has no field for it
  (MOD-spec-document, Data).
  - No test asks `parseSpec` to tell a process requirement from a product one, and the outcome drops "whether each
    constrains the product or the development process". Instead, a test reads this instance's SPEC.md with its
    `sources`; MOD-product-process takes its requirements as the process requirements.
  - A requirement missing a field is read with that field `null`. Naming it as a finding is the job of
    `requirementFindings`, which this item does not build.
- ITM-215:
  - Each rule the module's file names for `modelFindings` gets a definition that breaks it, including the four the item's
    list leaves out: a phase no transition reaches; a gate that checks a kind of artifact no earlier phase produces;
    pulled work with neither a time box nor a work-in-progress limit, or with both; a measure that does not fit the kind
    of work.
  - Since it realises `THE CATALOGUE IS DATA`, a test states that no model or practice name stands in the module's code.
- ITM-217: MOD-source-register checks no participant's place. `permittedPlaces` gives the places; checking a participant
  against them is the job of `eligible` (ITM-216, `Need.places`) and `declarationFindings` (ITM-218).
  - The criterion "a participant's place checked against them" leaves the item.
  - Its tests state `permittedPlaces` for four sources: one that may be republished (`any`), a restricted one with
    places, a restricted one with none, and one whose licence is `unknown`.
