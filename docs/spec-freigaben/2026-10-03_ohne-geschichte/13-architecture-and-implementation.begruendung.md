# 11. Architecture and implementation: no history

**The change.** 16 occasions removed; every source keeps who or what decided, without date or edit note. Every other rule and check is carried over byte for byte.

**Changed in this section:**
- `ONE MODULE, ONE FILE` removed — the name is not reused.
- `A MODULE IS A FOLDER` — replaces `ONE MODULE, ONE FILE`.
- `A MODULE STATES ITS RESPONSIBILITY AND ITS INTERFACES` — the decision that designs a module states it, with the formats of the files it reads and writes.
- `ARCHITECTURE RESTS ON ACCEPTED ARTIFACTS` — "or a module" removed: there are no module files.
- `THE DERIVATION RULES HOLD FOR ARCHITECTURE` — derivation of architecture decisions only: there are no module files.
- `AN ARCHITECTURE CHANGE IS NOT ACCEPTED WITHOUT AN IMPACT LIST` — a decision's impact: the modules it designs, their code files and tests, and the requirements.
- `AN IMPLEMENTATION JOB CHANGES ONLY ITS MODULES` — a code file belongs to a module by its folder.
- `MODULE GAPS ARE REPORTED, NOT FORBIDDEN` — "a code file that names no module" → "a code file outside every module's folder".

**Why.** The SPEC states only what holds now; its history is in git. Why a rule exists is recorded with the decision that accepted it, not beside the rule. The SPEC no longer cites SOFTWARE_MAINTENANCE.md: Agent M replaces it.
